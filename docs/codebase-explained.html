ITransferable.h

C++ חדש
החוזה האחיד לכל דבר שניתן לשלוח — קובץ, טקסט, או כל סוג עתידי. כל מי שרוצה לשלוח משהו חייב לממש ממשק זה. זהו לב ה-Open-Closed Principle בפרויקט: להוסיף סוג חדש = class חדש, לא שינוי בקוד קיים.

🔑 Open-Closed Principle

קוד פתוח להרחבה, סגור לשינוי. ITransport::send() מקבל ITransferable& — הוא לא יודע אם זה קובץ או טקסט. כשנוסיף ContactTransferable בעתיד — ITransport לא ישתנה בכלל.

#pragma once
אומר לקומפיילר: "טען קובץ זה פעם אחת בלבד". מונע הגדרה כפולה.
#include "IProtocol.h"
צריך את MessageHeader שמוגדר ב-IProtocol.h — כדי שנדע מה makeHeader מחזיר.
#include <vector> #include <cstdint> #include <string_view>
ספריות סטנדרטיות: vector לרשימת bytes, uint8_t לסוג byte, string_view לטקסט read-only.
ה-Interface עצמו
namespace BetterSend {
namespace = "מרחב שמות". כל קוד הפרויקט עטוף ב-BetterSend כדי למנוע התנגשות שמות עם ספריות אחרות.
class ITransferable { public:
הגדרת interface. ב-C++ אין מילת interface — ממשים עם class שכל הפונקציות שלו pure virtual. ה-I בשם = מוסכמה: "I" פירושו Interface.
virtual ~ITransferable() = default;
virtual destructor — חובה בכל interface.
בלי זה, אם נמחק ITransferable* שמצביע ל-FileTransferable, ה-destructor של FileTransferable לא יקרא ← דליפת זיכרון.
= default = "תן לקומפיילר לייצר מימוש ריק".
[[nodiscard]] virtual MessageHeader makeHeader( std::string_view senderName) const = 0;
[[nodiscard]]: warning אם קוראים ולא שומרים תוצאה.
virtual ... = 0: pure virtual — כל subclass חייב לממש.
string_view: טקסט read-only בלי copy — יעיל.
const: הפונקציה לא משנה את האובייקט.
[[nodiscard]] virtual std::vector<uint8_t> payload() const = 0;
מחזיר את ה-bytes לשלוח אחרי ה-header.
vector<uint8_t> = רשימה של bytes (uint8_t = מספר 0-255, גודל byte אחד).
לקובץ: תוכן הקובץ. לטקסט: UTF-8 encoding של הטקסט.
};
סגירת ה-class. נקודה-פסיק אחרי } היא חובה ב-C++ (שלא כמו ב-Java/JS).
} // namespace BetterSend
סגירת ה-namespace. ה-comment מזכיר לנו מה נסגר.

IProtocol.h

C++
מגדיר שני דברים: (1) MessageHeader — המבנה של header הודעה, (2) IProtocol — ממשק לקידוד ופענוח headers. הפרוטוקול רק אחראי על ה-header, לא על ה-payload.

🔌 Wire Format — פורמט ההודעה על הרשת

כל הודעה נשלחת כך:

[ 4 bytes: אורך ה-JSON ][ N bytes: JSON header ][ M bytes: payload ]

ה-4 bytes הראשונים הם big-endian uint32 — אומרים כמה bytes הוא ה-JSON. אז קוראים את ה-JSON (שמכיל סוג, שם, גודל, שם שולח), ואז את ה-payload עצמו.

MessageHeader — מבנה הנתונים
struct MessageHeader { enum class Type : uint8_t { File, Clipboard };
struct: כמו class אבל הכל public כברירת מחדל. משמש ל-data objects.
enum class: רשימת ערכים עם שם (type-safe). : uint8_t = יאוחסן ב-byte אחד.
שני סוגים: קובץ (File) וטקסט/לוח (Clipboard).
Type type{};
{} = אתחול ל-0 (ל-File). בלי זה — ערך לא מוגדר (undefined behavior).
std::string name; // Filename
שם הקובץ. ריק עבור Clipboard (אין שם קובץ).
std::size_t size{}; // Payload size in bytes
size_t = מספר חיובי בגודל המתאים לפלטפורמה (64-bit במחשב 64-bit). לא משתמשים ב-int כי גודל קובץ יכול לעלות על 2GB.
std::string senderName;
שם המכשיר השולח (מה שהמשתמש הגדיר, למשל "iPhone של יונתן").
IProtocol — ממשק הקידוד
[[nodiscard]] virtual std::vector<uint8_t> encodeHeader( const MessageHeader& header) = 0;
מקבל MessageHeader → מחזיר bytes לשלוח על הרשת.
const ... & = reference (לא copy) + לא ישתנה. יעיל לאובייקטים גדולים.
[[nodiscard]] virtual MessageHeader decodeHeader( std::span<const uint8_t> data) = 0;
span: "חלון" לתוך array קיים, בלי copy. בטוח יותר מ-raw pointer כי שומר גם את האורך.
זורק runtime_error אם ה-data פגום.

ITransport.h

C++
ממשק ה-Strategy לשכבת התקשורת. מגדיר מה Transport יכול לעשות, לא איך. המימוש הנוכחי: TcpTransport. בבדיקות: MockTransport.
Transfer — תוצאת קבלה
struct Transfer { enum class Type : uint8_t { File, Clipboard }; Type type; std::string senderName; std::string name; std::size_t sizeBytes{}; std::string data; };
מה שמגיע ל-callback כשמתקבלת העברה:
• type: קובץ או clipboard
• senderName: שם המכשיר ששלח
• name: שם קובץ (ריק ל-clipboard)
• data: לקובץ = נתיב שמירה, לטקסט = התוכן עצמו
ITransport — ממשק
virtual void startServer(int port, std::function<void(Transfer)> onReceive) = 0;
std::function<void(Transfer)>: סוג של callback — כל פונקציה שמקבלת Transfer ומחזירה void.
יכול להיות lambda, פונקציה רגילה, או method עם bind.
ה-callback יקרא מ-thread רקע — חשוב לסנכרון!
virtual void send(const std::string& ip, int port, const ITransferable& item) = 0;
OCP בפעולה: Transport לא יודע אם item הוא קובץ, טקסט, או כל דבר אחר. הוא פשוט קורא item.makeHeader() + item.payload(). להוסיף סוג חדש = לא לשנות שורה זו.
virtual void stop() = 0;
עוצר server ומחכה שכל ה-threads יסיימו (blocking). חובה לקרוא לפני השמדת האובייקט.

FileTransferable.h

C++ חדש
מימוש של ITransferable לקבצים. יודע לקחת path לקובץ ולספק header + bytes.
#include <filesystem> #include <fstream>
filesystem: C++17 — עבודה עם paths, גדלי קבצים. fstream: קריאת/כתיבת קבצים.
explicit FileTransferable(std::filesystem::path path) : path_{std::move(path)} {}
explicit: מונע המרה אוטומטית לא מכוונת (למשל string ← FileTransferable בטעות).
std::move: מעביר בעלות על ה-path בלי copy. יעיל.
MessageHeader makeHeader(std::string_view senderName) const override { return MessageHeader{ .type = MessageHeader::Type::File, .name = path_.filename().string(), .size = std::filesystem::file_size(path_), .senderName = std::string(senderName), }; }
override: אומר לקומפיילר "אני מוודא שזו באמת דריסה של פונקציה virtual מה-base". אם שגינו בשם — error.
.filename(): מחלץ רק שם הקובץ מה-path המלא (למשל /photos/cat.jpg → cat.jpg).
Designated initializers (.type=, .name=) — C++20.
std::vector<uint8_t> payload() const override { std::ifstream f(path_, std::ios::binary); if (!f) throw std::runtime_error(...); return std::vector<uint8_t>( std::istreambuf_iterator<char>(f), std::istreambuf_iterator<char>() ); }
קורא את כל תוכן הקובץ ל-vector של bytes.
istreambuf_iterator: iterator שקורא byte-by-byte מ-stream — הדרך הנפוצה לקרוא קובץ לvector.
std::ios::binary: חובה — בלי זה Windows ממיר \r\n ל-\n ופוגם בקבצים.
private: std::filesystem::path path_;
המשתנה היחיד: ה-path לקובץ. _ בסוף שם = מוסכמה לmember variables פרטיים.

TextTransferable.h

C++ חדש
מימוש של ITransferable לטקסט (clipboard). פשוט יותר מ-FileTransferable.
MessageHeader makeHeader(...) const override { return MessageHeader{ .type = MessageHeader::Type::Clipboard, .name = {}, .size = text_.size(), ... }; }
name = {}: string ריקה — לטקסט אין שם קובץ.
text_.size(): גודל ב-bytes של הטקסט (UTF-8 יכול להיות יותר bytes ממספר תווים).
std::vector<uint8_t> payload() const override { return std::vector<uint8_t>( text_.begin(), text_.end()); }
הופך string ל-vector של bytes. string הוא כבר UTF-8 ב-C++, אז פשוט מעתיקים את ה-bytes שלו.

מימוש של IDiscovery ל-macOS/iOS באמצעות Bonjour (dns_sd.h). עובד דרך mDNSResponder של המערכת — sandbox-compatible, לא דורש הרשאות מיוחדות.
MdnsDiscovery.cpp (raw UDP port 5353) משמש Android, Linux, Windows.

📡 Bonjour + AWDL — גילוי ללא WiFi משותף

ב-macOS, mDNSResponder מנהל את כל תעבורת ה-mDNS. ניסיון לקשור raw UDP לport 5353 נחסם על ידי ה-sandbox.
Bonjour API: מדבר ישירות עם mDNSResponder דרך Unix socket — sandbox-compatible.
AWDL (Apple Wireless Direct Link): רשת WiFi peer-to-peer ישירה בין מכשירים — ללא router. זו אותה טכנולוגיה שמשמשת AirDrop.
kDNSServiceFlagsIncludeAWDL: מרחיב את הגילוי מ"אותה רשת" ל"קרוב פיזית".
שרשרת הקריאות: Browse מוצא שם שירות → Resolve מוצא hostname:port → GetAddrInfo מוצא IP.

Shared Connection
DNSServiceCreateConnection(&mainRef_); static constexpr DNSServiceFlags kP2PFlags = kDNSServiceFlagsShareConnection | kDNSServiceFlagsIncludeAWDL | // peer-to-peer WiFi kDNSServiceFlagsIncludeP2P; // other P2P interfaces
kDNSServiceFlagsShareConnection: כל ה-sub-operations חולקים fd אחד.
kDNSServiceFlagsIncludeAWDL: מפעיל AWDL — מצא מכשירים קרובים ללא WiFi משותף, כמו AirDrop.
kDNSServiceFlagsIncludeP2P: ממשקים P2P נוספים.
Browse → Resolve → GetAddrInfo chain

מקבל שם שירות → מתחיל Resolve לקבלת hostname:port.
new ResolveCtx: מעביר את שם המכשיר הלאה בשרשרת — יימחק ב-resolveCb.
kDNSServiceFlagsAdd: מסנן רק מכשירים חדשים (לא "remove" events).
static void resolveCb(..., const char* hosttarget, uint16_t port, ...) { auto* ac = new AddrCtx{rc->state, rc->serviceName, ntohs(port)}; delete rc; DNSServiceGetAddrInfo(&addrRef, kDNSServiceFlagsShareConnection | kDNSServiceFlagsTimeout, ifIdx, kDNSServiceProtocol_IPv4, hosttarget, addrInfoCb, ac); }
מקבל hostname:port → מבקש IP.
ntohs(port): ממיר מ-network byte order (big-endian) ל-host byte order.
kDNSServiceFlagsTimeout: אם לא נמצא IP בזמן — callback עם שגיאה (לא תקוע לנצח).
static void addrInfoCb(..., const sockaddr* addr, ...) { inet_ntop(AF_INET, &sin->sin_addr, ipbuf, ...); ctx->state->onFound(Device{ctx->serviceName, ip, ctx->port}); DNSServiceRefDeallocate(sdRef); delete ctx; }
סוף השרשרת: יש שם + IP + port → בונים Device וקוראים ל-callback.
inet_ntop: ממיר כתובת IP בינארית ל-string קריא.

inline constexpr char kBleServiceUuid[] = "5BE77ECD-A1B2-4F1A-8C5D-7F8E9D2C4A6B"; inline constexpr uint16_t kBleCompanyId = 0xFFFF; inline constexpr uint8_t kBleMagicBytes[] = {0xBE, 0x77, 0xEC, 0xD0}; inline constexpr int kBleMaxNameLen = 20;
kBleServiceUuid: GATT service UUID לשלב ה-handshake (read SSID+PSK אחרי שהצד השני נמצא). לא נכנס לתוך ה-advertise כי 128-bit לבד תופס 18 בייטים — לא משאיר מקום לשם בתוך 31 הבייטים הלגאסי.

kBleMaxNameLen 20: גודל מקסימלי לשם מכשיר בתוך ה-advertise (3 AD Flags + 8 ManufacturerData overhead + magic = 15 כבר תפוסים, 31-15 = 16 לשם; שמרנו 20 לבטיחות עם חיתוך).

🛰️ רקע — איך BLE Advertising עובד

Phase 1
שני המימושים של IDiscovery בPhase 1 (BleDiscovery_Windows + BleDiscovery_Mac) בנויים מעל מספר מושגים של Bluetooth Low Energy. הסיכום הזה מסביר את הבסיס בצורה פשוטה כדי שיהיה יותר נוח לקרוא את הקבצים בהמשך.

מקורות לעומק:
  • Microsoft Learn — BLE Overview (Windows / WinRT)
  • Apple — CoreBluetooth Programming Guide
  • Bluetooth Core Specification (המקור הרשמי, ~3000 עמודים)
  • Silicon Labs — Bluetooth 101 (מבוא קצר וקריא)
Bluetooth Classic ← אוזניות, רמקולים, mouse — תקשורת קבועה Bluetooth Low Energy (BLE) ← beacons, smart watches, BetterSend
אנחנו ב-BLE. ההבדל המעשי: צריכת חשמל נמוכה משמעותית, יכולת ל-"לשדר בלי חיבור" (advertising mode), טווח של ~10-30 מטר. אותו chip בלוטות' תומך בשני המצבים — שונה רק האופן שבו הוא משדר.
┌──────────────────────────────────────────┐ │ Primary advertisement (31 בייטים max) │ ←─ נשלח כל ~100-200ms ├──────────────────────────────────────────┤ │ Scan response (31 בייטים max, optional)│ ←─ נשלח רק כש-scanner ביקש └──────────────────────────────────────────┘
ה-"שידור" ב-BLE legacy הוא פקטה של עד 31 בייטים. אם רוצים יותר, ה-peripheral יכול לשלוח scan response — פקטה שנייה (עוד 31 בייטים) רק אחרי ש-scanner ביקש אותה. ה-scanner מבקש אם הוא ב-active scan mode — שולח SCAN_REQ. ב-Windows זה ScanningMode::Active; ב-CoreBluetooth זה default.

סה"כ עד ~62 בייטים בלגאסי. BLE 5.0 הוסיף extended advertisements עד 255 בייטים — תמיכה יחסית חדשה. הקוד שלנו מפעיל אותה ב-Windows (AllowExtendedAdvertisements(true)) ליתר ביטחון.
Advertisement data := concat of AD structures, כל אחד: [1B length][1B AD type][data bytes] AD types שאנחנו משתמשים בהם: 0x01 Flags ← ה-OS מוסיף אוטומטית, סה"כ 3B 0x07 Complete 128-bit UUIDs ← 1+1+16 = 18B לכל UUID 0x09 Complete Local Name (N) ← 1+1+N = N+2B 0xFF Manufacturer Data (N) ← 1+1+2+N = N+4B
כל AD section מתחיל ב-2 בייטים מטא (length + type), ואחריהם ה-payload. UUID של 128-bit לבד אוכל 18 בייטים — רוב התקציב. ManufacturerData עם CompanyID + magic + שם של 10 תווים אוכל 18 בייטים. שניהם ביחד עם Flags = 3+18+18 = 39 → overflow, ה-OS דוחה.

זו הסיבה שהקוד שלנו אסימטרי: אנחנו לא יכולים לדחוס את כל המידע (UUID + שם) לpacket אחד, אז כל פלטפורמה משתמשת במה שעובד אצלה.

הבדל פלטפורמתי קריטי: Apple מתעלמת בשקט מ-ManufacturerData ב-advertise. ה-API מקבל בלי שגיאה, אבל הבייטים פשוט לא יוצאים מהמכשיר. ה-תיעוד הרשמי של Apple מציין: "peripheral devices using Core Bluetooth can only specify a subset of these types" — והרשימה כוללת רק LocalNameKey ו-ServiceUUIDsKey.

לכן הקידוד שלנו אסימטרי בכוונה: Mac משדר ServiceUUID + LocalName, Windows משדר ManufacturerData. שני הצדדים יודעים לקרוא שתי החתימות בצד ה-scan.

למה control plane: דחיפת קבצים בלי הסכמה זה חוויית AirDrop שבורה. ב-Phase 1 v2 השליחה היא 4-שלבית: (1) sender שולח request, (2) receiver UI מציג AlertDialog, (3) receiver שולח accept/decline, (4) רק על accept — sender שולח את הקובץ.

למה JSON-in-Clipboard ולא ערך wire חדש: שמירת הפרוטוקול הקיים פנוי לשינויים עתידיים (encryption, chunked, etc.). ה-control נושא prefix "BS\t" שמבחין אותו מ-Clipboard רגיל באופן חד-משמעי (TAB לא מופיע ב-Hello sentinel ולא בטקסט normal).

State: pendingOutgoing/pendingIncoming maps ב-BetterSendContext, מוגנים ב-transfersMu. transferId נוצר ב-Dart (timestamp_us + random hex), שולח לnative דרך bettersend_send_file.
